## Задача 2

1. Для задачи требующей использования высоконагруженной базы данных MySql, критичной к отказу, оптимальным выбором будут физические сервера.

Определяющие критерии выбора:
- максимальная и предсказуемая производительность
- высокая стабильность
- изоляция ресурсов, исключающая утилизацию ресурсов другими "соседями"
- прямой доступ к оборудованию, позволяющий использовать производительные RAID-контроллеры или шину PCIe

2. Для задачи требующей запуска различные web-приложения, оптимальным выбором будет виртуализацию уровня ОС.

Определяющие критерии выбора:
- максимальная плотность и экономия ресурсов
- мгновенный запуск и масштабирование, что позволяем быстро справиться с наплывом пользователей
- изоляция и CI/CD процессы, приложение изолировано в своем контейнере со всеми своими зависимостями

3. Для задачи требующей запуска Windows-системы для использования бухгалтерским отделом, оптимальным выбором будет паравиртуализация.

Определяющие критерии выбора:
- нативная и стабильная поддержка Windows
- гибкое управление ресурсами, позволяющее оперативно (на лету) изменить параметры сервера (vCPU, RAM), в зависимости от ситуации
- резервное копирование, позволящее мгновенно восстанавливать сервер целиком из бэкапа
- технологии High Availability (HA), позволяющая быстро развернуть ВМ на другом сервере кластера

4. Для задачи требующей запуска систем, выполняющих высокопроизводительные расчёты на GPU, оптимальным выбором будут физические сервера.

Определяющие критерии выбора:
- прямой доступ к PCIe и NVLink
- использование нативных технологии уровня железа, таких, как GPUDirect RDMA
- эффективность охлаждения и питания, контроль частот и управление питанием на физическом уровне работают наиболее предсказуемо

## Задача 3

1. Для сценария подразумевающего 100 виртуальных машин на базе Linux и Windows, общие задачи, без особых требований. Где преимущественно используется Windows based-инфраструктура, и требуется реализация программных балансировщиков нагрузки, репликации данных и автоматизированного механизма создания резервных копий, оптимальным выбором будет Microsoft Hyper-V.

Определяющие критерии выбора:
- бесшовная интеграция с Windows-инфраструктурой
- встроенный балансировщик нагрузки SLB
- встроенная функция Hyper-V Replica
- Windows Server Datacenter позволяет запускать безлимитное количество виртуальных машин Windows Server на лицензированных физических хостах

2. Для сценария требуещего наиболее производительное бесплатное open source-решение для виртуализации небольшой (20-30 серверов) инфраструктуры на базе Linux и Windows виртуальных машин, оптимальным выбором будет Proxmox VE (KVM).

Определяющие критерии выбора:
- максимальная производительность (KVM интегрирован напрямую в ядро Linux), что обеспечивает минимальные накладные расходы на виртуализацию и скорость работы ВМ
- 100% бесплатный Open Source, нет искусственных ограничений на количество процессоров, объем ОЗУ или функции
- отличная поддержка Windows, благодаря использованию драйверов VirtIO

3. Для сценария тербующего бесплатное, максимально совместимое и производительное решение для виртуализации Windows-инфраструктуры, оптимальным выбором будет Proxmox VE (KVM).

Определяющие критерии выбора:
- максимальная производительность (KVM интегрирован напрямую в ядро Linux), что обеспечивает минимальные накладные расходы на виртуализацию и скорость работы ВМ
- 100% бесплатный Open Source, нет искусственных ограничений на количество процессоров, объем ОЗУ или функции
- отличная поддержка Windows, благодаря использованию драйверов VirtIO

4. Для сценария требующего рабочее окружение для тестирования программного продукта на нескольких дистрибутивах Linux, оптимальным выбором будет совместное использование VirtualBox Vagrant Docker (Docker при определенных сценариях можно использовать отдельно).

Определяющие критерии выбора:
- максимальная гибкость дистрибутивов
- удобный мехнизм создания снапшотов
- автоматизация через Vagrant

## Задача 4

Использование гетерогенной среды виртуализации, как правило, требует компромисса между экономией на лицензиях и усложнением инфраструктуры.

Проблемы и недостатки гетерогенной среды:
- сложность управления, отсутствие «единого окна» для мониторинга, оркестрации и управления
- высокие требования к компетенциям ИТ-команды, администраторы должны одинаково хорошо разбираться в архитектуре, тонкостях настройки и траблшутинге нескольких разных платформ
- проблемы с миграцией и совместимостью, перенос ВМ требует конвертации дисков и адаптации гостевой ОС, что приводит к простоям
- сложность резервного копирования, конфигурация политик, глубина интеграции и лицензирование будут отличаться, что усложняет аудит безопасности данных
- фрагментация ресурсов и избыточность, сложнее балансировать нагрузку, требуется держать избыточный резерв
- разрозненная сетевая связанность и безопасность

Минимизировать риски и проблемы при проектировании гетерогенной среды виртуализации можно следующими шагами:
- четкое разделение по критичности (эшелонирование), закрепление за каждой платформой свой класс систем
- внедрение CMP (Cloud Management Platform), которые умеют оркестрировать разные гипервизоры из одного интерфейса
- использование универсальных инструментов мониторинга и бэкапа
- максимальная стандартизация гостевых ОС

Несмотря на очевидность выбора в сторону построения монолитной среды, бывают сценарии, при которых гетерогенная среда будет более оптимальна, например:
- масштабные Dev/Test контуры, в которых держать тестовые ВМ на дорогой enterprise-платформе экономически нецелесообразно
- защита от Vendor Lock-in, требующая поддержки второй (альтерантивной) платформы в состоянии «warm standby» (готовой к приему нагрузок)

Поэтому мой выбор бы строился прежде всего исходя из критериев ифраструктуры.
